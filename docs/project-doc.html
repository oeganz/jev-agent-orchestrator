Overview

The fleet is a multi-agent orchestrator that lives in this directory. Its single contract is in fleet-orchestrator/SKILL.md, and the orchestrator session loads it on start. The harness dispatches work to planner, engineer, tester and devops workers and reviews their output through gates.

The one-line contract: "Implementation goes to workers". The orchestrator only acts when the fleet cannot, and gate review authorizes synthesis, never an edit.

Run-store layout

Every run lives at fleet/runs/<run-id>/ and contains:

  • run.json — objective, status, mode, optional orca_run id.
  • tasks.jsonl — one JSON row per dispatch.
  • gates.jsonl — one JSON row per gate decision and per orchestrator-direct action.
  • reports/ — the worker reports that gate decisions read.

summary.md is created at run end and becomes the consolidated report (its presence is what fleet runs reports as summary yes).

At the time this doc was generated the fleet had 11 runs — this is what runDirs() counts when fleet status prints the runs line. A curated example active run is 20261004-0200-rework-loop.

Architecture

The orchestrator is one role; the harness runs six worker roles: planner, engineer, tester, devops, and the 7b reviewer. Each role has its own SKILL.md under .claude/skills/fleet-*; the orchestrator loads them on dispatch.

Two dispatch mechanisms

The default is Claude Code subagents: engineers run in place, one writer at a time, and testers run in a fresh agent with isolation: "worktree". Subagents close themselves when done but die with the parent session, so there is no resume path for them.

Orca orchestration is kept for two cases only: a reviewer that must be provably unable to write, and a long run that must survive the session (where fleet resume takes over).

An Orca run MUST be bound first: orca orchestration run-create --objective "<obj>" --json sets run.json.orca_run; without it worker-start fails with consumer_fenced. The Run id comes back at result.run.id in the JSON envelope.

Module map

fleet/bin/fleet.mjs is the CLI entry point; lib helpers start at SOURCES (the source vocabulary code | config | doc | inferred that REQUIRED_META_KEYS names the keys every doc-meta must carry). The lib modules referenced from the SKILL.md:

  • fleet/bin/lib/jev.mjs — the JEV client (askJev, gateVerdict).
  • fleet/bin/lib/jev-router.mjs — skillCatalog, buildRouteQuestions, routeDecision.
  • fleet/bin/lib/orca.mjs — resolveOrca, orcaStatus, settleSnapshot.
  • fleet/bin/lib/doctor.mjs — fsChecks + commandResolves for fleet doctor.
  • fleet/bin/lib/project-doc.mjs — extractClaims, validateDoc, gapReport for this doc.

The Loop and Gates

The orchestrator skill names a numbered loop. Step 1 is Intake — restate the objective, pick a shape (small inline, planner, devops, or reviewer), and ask the user before spending anything if anything is ambiguous. Step 2 creates the run (run.json + tasks.jsonl + gates.jsonl + reports/). Step 3 is the per-task preflight (tree clean, secrets excluded, base_sha recorded, every dispatch gets a tasks.jsonl row including testers and reworks). Step 4 dispatches (4a subagent, 4b Orca), Step 5 waits, Step 5c asks JEV, Step 6 is G2, Step 7 dispatches the tester, Step 8 is G3, and Step 9 reports and settles.

Gates G0 through G4

The modes.auto.gates list is ["G0","G1","G2","G3"]; G4 is always human. Each gate has its own role:

  • G0 budget — advisory while budget.daily_cap is null.
  • G1 plan — review planner specs before any dispatch.
  • G2 build — a mechanical per-task check; JEV only when the change is high-risk or the evidence is ambiguous.
  • G3 verify — JEV decides the tester's report.
  • G4 irreversible — human only; JEV is OFF (gates_jev.G4 = false).

gates_jev names which gates route to JEV; the keys are G1, G2, G3 = true, G0, G4 = false.

G2 / G3 policy table

The policy reads as it does today, from gateVerdict() and the orchestrator skill:

BranchWhat happens
JEV degraded / unavailable Orchestrator reviews it fully (NEVER auto-pass).
Malformed answers Orchestrator reviews it fully (six distinct malformed-* branches).
Any flag > 0.55 NOT accept; orchestrator reviews (flag-first, the choice cannot override).
chosen-prob < 0.60 Orchestrator reviews fully (the CHOSEN route option, not the max).
Any flag in 0.40–0.60 Orchestrator reviews fully (uncertain band).
Choice is not decisive Orchestrator reviews fully (only accept / pass / verified / rework / rework-needed are decisive).
chosen-prob < 0.80 Orchestrator reviews fully (below auto_apply).
else Follow the JEV verdict.

Settle & hard rules

Hard rule 2 is mechanical: never end a turn with a reclaimable or leaked Orca worker, run fleet settle after every gate decision. cmdSettle is the implementation; one run previously leaked 14 live claude processes / 4.4 GB before settle was made a command.

The remaining hard rules: fleet first, never implement what the fleet can do; never accept success from prose, reproduce the evidence; never dispatch onto a dirty tree without a checkpoint; never run concurrent writers in one workspace; budget — G0 is advisory until calibrated; irreversible actions are G4, the human decides.

JEV

JEV (TypeSafe System One) is a calibrated decision model, not a language model. It returns probabilities, never prose. The API exposes three primitives:

  • noul — a yes/no probability (0–1; 0.5 = equal odds, not "medium"; no bands inside it).
  • choice — which of N options, with an always-included none_fit abstain option.
  • score — a 2–10 level rubric whose criteria is an ARRAY, not an object.

Measured thresholds

The thresholds the harness uses today:

ThresholdValueSource
flag 0.55 Measured 12/12 at 0.50–0.60; 11/12 at 0.7
abstain 0.60 Single route error returned 0.28
auto_apply 0.80 "start conservative; lower as override rate falls"
uncertain_band 0.40–0.60 Route to deeper review
routing.auto_apply 0.65 Calibrated on 2026-10-07 with 14 cases
routing.abstain 0.60 multi_threshold 0.65

The default values on gateVerdict() mirror the config: flag 0.55, abstain 0.6, autoApply 0.8, band [0.4, 0.6], decisive ['accept','pass','verified','rework','rework-needed'].

The router

skillCatalog(dirs) walks <dir>/<skill>/SKILL.md and lifts the single-line description: frontmatter field. The shape is the same as a JEV choice criteria object. buildRouteQuestions({id, instructions, options, multi}) builds one choice question plus (when multi=true) one noul per option, with a none_fit always-presented abstain. routeDecision() resolves the answer and returns decided_by, the chosen probability, and (when calibrated) the multi list.

Calibration was measured at 14 cases on 2026-10-07 with choice accuracy 92.9% (the 14/14 minus one — live-measured; see the orchestrator skill, section 5c recipe 1).

Deletion detection

JEV's deleted_out_of_scope noul is ADVISORY, not the deletion gate. The deterministic gate lives in code: parseDiff() parses a unified diff, deletedLines() flattens it, and unmatchedDeletions() drops every deletion that has a plausible rewrite in the same hunk (polarity-guarded). deletionCheck() is the orchestrator-level wrapper that flags when the unmatched-line count and ratio both exceed the cut.

Two measured incidents

  • Per-criterion nouls pinpointed WHICH criterion lacked evidence (0.56) on T4; the old generic "any unmet?" noul could not name the criterion.
  • Generic evidence_gap fired on clean work at 0.63/0.73/0.69 (T7), 0.75 (T9), 0.47 (T1) while every per-criterion noul was ≤ 0.20 — it reacted to the NUMBER of side claims in a long report.
  • JEV's deleted_out_of_scope noul scored 0.56 on a real T9 deletion but 0.64 on legitimate T1 rewrites — it cannot separate; the deterministic count can (T9 58/63, T1 3/13, T2 1/6).
  • A 41-line deletion outside scope was missed by the constraint noul (0.12) but flagged by the deterministic count — the documented grep "^-[^-]" dropped 17 of 71 deletion lines, including section-6 ALWAYS rules.

Config keys that matter

  • mode — currently "auto"; the modes object lists which gates run.
  • irreversible_actions — deploy, push, force-push, delete-data, infra-change, spend-above-cap (G4).
  • budget.daily_cap — null = UNC ALIBRATED, G0 is advisory.
  • jev.model — "jev-1-13-free".
  • jev.providers — primary + OpenRouter fallback (metered).
  • jev.routing — the calibrated thresholds.
  • gates_jev — which gates route to JEV.

Known failure modes

  • Orca worker-start fails with consumer_fenced when the orchestrator has not run run-create for this session.
  • JEV 429 / 529 responses retry once then degrade; three consecutive failures open the per-provider circuit breaker for 5 minutes so later gates short-circuit.
  • .cmd / .bat files are NOT runnable by Node 24 execFileSync; commandResolves() refuses to mark a batch file as resolved so doctor does not lie.
  • Subagents die with the session; there is no fleet resume path for them — the orchestrator checks git log against the row's base_sha and re-dispatches with rework_of.
  • Subagents inherit the session's bypass permissions — the orchestrator's own git diff / git status at every gate is the backstop, not a prevention.

Glossary

TermMeaning
gate A decision point between steps (G0 budget, G1 plan, G2 build, G3 verify, G4 irreversible)
noul A yes/no probability from JEV (0–1; 0.5 = equal odds)
choice JEV question over N options (object criteria, always with none_fit)
score JEV rubric over an ARRAY criteria; 2–10 levels
claim A span tagged class="claim" with data-claim, data-source, and data-evidence
worker_done For a subagent, the agent's final reply; for Orca, the worker_done event in check --wait
reclaimable An Orca worker in terminalState: 'reclaimable' — fleet settle releases it.
settle Release every reclaimable worker; archive-then-close live user_takeover leaks
escalation A branch in routeDecision() or gateVerdict() where decided_by !== 'jev''
G0–G4 Five gates the loop runs (G4 human only)
JEV TypeSafe System One — https://.id/v1/systemone
Orca The persistent orchestration runtime that survives the Claude session
